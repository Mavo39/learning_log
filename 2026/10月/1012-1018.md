## 10/12(月)

- プログラムファイルがメモリにロードされる際、実行ファイル全体がディスクから物理メモリに一括コピーされるわけではなく、OSは仮想アドレス空間を構成し、実行に必要なページを必要に応じて物理メモリに読み込む。実行ファイルのコードなどは、メモリマッピングやページフォールトの仕組みを通して読み込まれる
- Copy-on-Write（COW：書き込み時コピー）は子プロセスが共有ページを変更する必要が生じたときに、OSが子プロセス側のコピーを作り、変更をそちらに反映させること。ただし、これは通常の `fork()` で作られたプロセスのメモリについての話である点に注意
- プログラムイメージ: プロセスが実行するプログラムを構成するコードやデータなど
- `static` は共有を実現する仕組み(Java)
- クラスが管理すべき内部状態を外部に直接操作させていいのかどうかを判断する
- オブジェクト指向の `private` が制限するのは「インスタンス」ではなく "クラスの外部" であるため、同じクラスの別のインスタンスはアクセスできる（`private` フィールドでも、同じクラスのメソッドなら別のインスタンスの値を扱うことができる）→ クラス単位のアクセス制限
- 「クラス内部からのみ使用できる」= 同じクラスの別のインスタンスはアクセスできる
- 注意点: `private` が判断するのは "どのインスタンスを操作しているか" ではなく、基本的に "どのクラスのコードからアクセスしているか" ということ 
- 「クラスの外部」とは、"クラスの定義の外側" という意味: 別のクラスであるクラスのインスタンスを使用する場合、このクラス内からインスタンスの `private` 修飾子がついたフィールドやメソッドはアクセスできないということ
- `private` であっても、その値を外部に一切渡せないわけではない。直接アクセスは制限されるが、クラスが公開したメソッドを通じて値を取得することはできる = インスタンスを作成した場所によって、そのインスタンスの `private` へのアクセス権限が変わるわけではない
- クラスやインスタンスを箱ととらえ、箱の中に箱を作っても外側の箱から直接操作できるかどうかは 公開 or 非公開 の設定で決まる、と考えることで思考が整理された
- アクセスメソッドやミューテータメソッドを用意すれば、外部からデータを取得したり変更したりできるため、カプセル化の意味がないのでは？と思った。しかし、カプセル化する意味があるのは、単に変更を禁止するためではなく、"どのような方法で変更できるか" をクラス側で制御できるようにするためであると知った。内部の状態をルールに従って変更できるように制御する。許可の範囲をクラスで決めることができる。

```java
// 例1
class Person{
    private String firstName;
    private String lastName;

    public Person(String firstName, String lastName){
        this.firstName = firstName;
        this.lastName = lastName;
    }

    // firstNameのゲッター
    public String getFirstName(){
        return this.firstName;
    }

    // firstNameのセッター
    public void setFirstName(String firstName){
        this.firstName = firstName;
    }

    // lastNameのゲッター
    public String getLastName(){
        return this.lastName;
    }

    // lastNameのセッター
    public void setLastName(String lastName){
        this.lastName = lastName;
    }

    // toStringメソッドをオーバーライド
    @override
    public String toString(){
        return this.getFullName();
    }

    private String getFullName(){
        return this.firstName + " " + this.lastName;
    }
}

class Main{
    public static void main(String[] args){
        Person carly = new Person("Carly", "Angelo");

        // toString() は公開メソッドだが、getFullName() は非公開メソッドだけど、これで表示ができるのはなぜ？
        // → private のアクセス制限は、そのメソッドを呼び出すコードに対して適用されるから
        System.out.println(carly);
    }
}
```

- この例1の設計の場合、Mainクラスでフルネームを組み立てる処理を書かせていないため、フルネームの組み立て方を変更したい場合、Personクラス内部を修正するだけで済む → 非公開メソッドは外部から直接使わせなくても、公開メソッドの内部処理として活用できる
- 「セッターがないこと」と「値を絶対に変更できないこと」は、必ずしも同じではないことに注意
- 配列を返すときは注意が必要、元の配列に影響があるとまずいときは複製を作ること
- クラス内部で使うメソッドを追加することと、外部に公開する契約を変更することは別
- 「内部の実装を変えること」と「クラスを使う側から見た約束を変えること」を分けて考えることで間違いを防ぐことができた
- 複数の似た処理がある場合に関数で共通化できないか考えがちだが、判断基準として "コードが重複しているか" だけでなく、"共通する処理に意味のある名前をつけることで、コード全体の意図が読みやすくなるか" を考える必要があるとわかった
- 自分でクラスを実装するときは、すべてをゼロから作るのではなく、既存のクラスに任せられる処理と、自分が実装すべき処理を切り分けることが重要。自分で実装しようとしてしまう傾向があるとわかった。


## 10/13(火)

- `switch` 文をつかうときは必ず `default` をつけること→想定外の値がきたときのための対策
- 明確な境界線を引くために目的を整理することがバグの温床を防ぐと、メイン関数があるバージョンとないバージョンを比較してわかった
- また、グローバル変数の書き換えリスクについても考える必要があるため、何も考えずグローバル環境に変数を定義するのはやめていこう
- メイン関数を用意して入り口を明示すること
- 外側のスコープにある変数であれば、関数の中から直接読み書き（代入）できてしまい、予期せぬバグの原因になりやすいため、基本的には関数内で外側の変数を書き換えない（ローカル変数として閉じる）書き方が推奨される
- PythonやPHPではブロックではスコープがつくられないため、スコープを表現するために関数の中に関数を書く
- 関数をつくるときには、何を渡したら何が返るのかという関係が明確になることにすること
- 計算する処理と状態を変更する処理を分けて考えると、コードの流れを追いやすくなるため可読性が上がる
- 配列の特徴として、同じような意味を持つ値を順番に並べるのが得意というのがある


## 10/14(水)

- Web API はデータそのものではなく、データをやり取りするための窓口・仕組み
- データをまとめるときは、ただまとめるのではなく、そのデータの意味が分かる形でまとめること
- 構造体: 関連する型を一つの型としてまとめる
- JSON: そのデータを文字列として表現し、別のプログラムなどに渡せる形式
- クラスで定義するメリットは、同じ属性のデータが増えた時の管理がしやすくなること、都度変数を作成すると管理が大変なだけでなく、関数に渡すときもハードコーディングになってしまい、変更があると一気に大変になってしまう
- オブジェクトとインスタンスは同じものくらいの認識だったが、インスタンスは "どのクラスから作られたのか" を言いたいときに使う呼び方であるということがわかった
- 関連するデータと処理を適切にまとめ、変更箇所を局所化できるように設計することが重要
- また、"どのデータ" を "どの処理が扱うのか" を明確にし、変更の影響範囲を制御しやすくすることも大事
- オブジェクト指向をつかう目的は、システムが大きくなっても理解・変更・拡張しやすい構造を作ること。改修コストを下げることばかりを考えていたので良い発見だった
- メソッドを記述する前に、その処理は本当にこのクラスの役割なのかを考えることが重要
- `@staticmethod` をつけると "インスタンス化せずに使う関数" という意図がコードから読み取ることができる


## 10/15(木)

-  `try-except` を関数内で定義した処理で、`try` `except` 両方で `raise` をした場合、引数なしの raise は、現在捕捉している例外を再び送出する命令になる。つまり、新しい例外を発生させず、既存の例外を再創出しているに過ぎないということ
- `raise` のあとに指定した種類の例外オブジェクトが作成され、それがバケツリレーのように繋がっていく
- エラーハンドリング: 失敗したときの動きを決めておくこと
- "入力内容が正しいか" と "例外が起きること" は別物
- `except Exception:` Exception: すべての種類のエラーをまとめて捕まえるという意味
- 失敗した場合はどうするかまで考えることが課題
- デバッグするときにはどこまでが正しく、どこからが期待したものと違うのかという視点を常に持つこと。闇雲に原因を探さないこと、範囲を徐々に狭めていくこと
- テストするときには境界の前後(if文の内容考慮)を確認すること
- `assert` は入力検証とは別で、開発者がこうなっているはず、と確認する目的で使われることが多い（"条件が成立するはず" という前提を確認するための仕組み）
- ターミナルやコマンドラインから入力された値は、基本的にすべて文字列として受け取るため、必要に応じてキャストが必要
- メンバ変数として定義したからといって、必ずすべてをコンストラクタで初期化する必要はない
- 初期化するかどうかは、そのオブジェクトが生成された時点で、どのような状態であるべきかという設計上の判断
- メンバ変数として保持するかどうかは、"オブジェクトがその情報を生成後も状態として保持する必要があるか" で判断する

## 10/17(土)

- ウィジェット（Widget）: GUIを構成する画面の部品（パーツ）の総称
- イベントハンドラ（Event Handler）: 特定のイベントが発生したときに実行する処理のこと（※イベントは "起きた出来事"、イベントハンドラは "その出来事に対応する処理"）

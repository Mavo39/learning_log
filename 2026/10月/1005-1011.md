## 10/9(金)

- オブジェクト指向において、1つのオブジェクトの中にプロパティ（データ/状態）とメソッド（処理/振る舞い）をまとめて持たせる（カプセル化する）最大の理由は、状態の不正な書き換えを防ぎ、関連するデータと処理を一箇所に集約することでプログラムの変更や管理を容易にすること = データと処理をセットにして「まとまり」を作る→明確な境界が生まれる
- メンバ変数とプロパティは厳密には異なるらしい
- メンバ変数（フィールド）: クラス内部でデータを保持する変数そのもの（記憶領域）
- プロパティ: メンバ変数へのアクセスを制御する仕組み（Getter / Setter など）。外部からは変数のように見えるが、内部的にはメソッドのように動作させることができる
- メンバ変数 = 実体となるデータそのもの
- プロパティ = そのデータに安全にアクセスするための窓口（仕組み）
- 言語が設計上どのようにオブジェクトの等価性を定義しているかによって、オブジェクトの比較の仕方が変わる
- S3から自動的にCSVファイルを読み取るまでの流れとS3にないデータはRedshiftから自動的にどのようにアンロードしているかの仕組みがまだ理解できていない点が今後の課題の1つ
- 従来型のロジックでは同じファイルをわざわざ手作業で作ってそれをベースに処理をするものがあったので、その点を来週改修することにした
- 改修や新規でロジックを作成するときに常に意識するのは、引継ぎ前提で初めて扱う人でも理解できるように意図や処理の流れを明確にすること


## 10/10(土)

- PATH を通す必要があるのは "コマンド（実行ファイル）" だけ
- この辺りの基礎が抜けているとわかったので都度吸収していこう
- PATH の役割: ターミナルで `python` や `pip` と打ったときに、どの仮想環境の実行ファイル（インタープリタ）を呼び出すかを OS に教えるためのもの
- 実行ファイル / バイナリ: OS（WindowsやMacなど）が直接理解して起動できる "プログラム本体"。中身は人間が読めない0と1の機械語で書かれている。中身を上から順に読み込み、機械語に翻訳しながらCPUに命令を出す作業員。
- スクリプト: 人間が読み書きできる日本語や英語のようなテキスト（文字情報）の集まり。OSから見ると、メモ帳で作った .txt ファイルと本質的な違いはない。単体ではOSから直接実行できない。作業員に対する "指示書"
- シャローコピー: 入れ物だけを新しく作り、中身の参照アドレスをそのままコピー = コピー元のオブジェクトと同じ参照を持つ
- ディープコピー: 内部にある参照先データもすべて辿り、新しくメモリを確保して丸ごと複製する = メンバ変数は同じでも別オブジェクトとして複製
- コンピュータにとって重要なのは、ビットの並びをどのルールで読むか = 「ビット列 × ルール = 意味」
- プログラムはどのようなデータを持ち、それをどのように処理するかを決めること
- 型が決めるのは「何ができるか」（値に種類を持たせている）= その値に対して何ができるか
- 型を決めるときは、そのデータが何を意味し、どんな操作をしたいのかという目的から考える（データの意味と扱い方を明確にする）
- 累乗は桁の重み、その桁が全体の数値の中でどれだけの価値（重み）を持っているかを表す（10進数: 基数=10, 2進数: 基数=2）
- コンピュータのCPU内部（ALU：演算装置）では、引き算専用の回路（減算器）を作らず、加算器（足し算回路）だけを使ってすべての引き算を実行している
- 短距離走的な考え方と長距離走的な考え方があり、個人的には長距離走的な考え方が重要な気がした（設計と整合性だけを厳格に理解する）
- 限られたビット数では正確に表せない値が存在する、だから、10進数の計算ではうまくいくのにコンピュータ上では表現できない、変な誤差が生じることがある
- Unicodeのコードポイントをバイト列に変換するルールの一つがUTF-8

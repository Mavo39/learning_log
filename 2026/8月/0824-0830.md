- リポジトリ：ファイル ＋ 隠しフォルダ（.git）で、「いつ・誰が・何をどう変更したか」という過去すべての履歴が保存されている
- つまり、`git init` というコマンドを実行することにより、普通のフォルダの中に .git という隠しフォルダが生成され、その瞬間からそのフォルダが "リポジトリ" へと変化する
- `git add .` は「変更があったファイルをマークする」だけではなく、「その瞬間のファイル内容（スナップショット）をパシャリと切り取ってインデックスに差し出す操作」を行なっている

- どんなデータ構造からでも、順に1つずつデータを取り出す共通の仕組み（取り出し係）のことをイテレータという
- 「いまどこを見ているか（現在はノードA）」という現在地を記憶し、リクエスト（`next()`）されるたびに「現在のデータを渡して、視点を次のノードBへ進める」という動作を行なう仕組み
- ジェネレータは、イテレータを非常に短いコードで簡単に作成するための機能

```sh
[ パッケージ (Package) ]
  └── ディレクトリ (フォルダ)
        ├── __init__.py
        ├── module1.py  ← [ モジュール (Module) ]
        └── module2.py  ← [ モジュール (Module) ]
```

- `__init__.py` は、インタープリタに「このディレクトリ（フォルダ）は Python のパッケージだ」ということを教えるための特別なファイル。このファイルがディレクトリ内にあることで、インタープリタはフォルダではなく、`import` できるパッケージとして認識する
- `__init__` がない場合でもインスタンス化は可能
- データベースにおけるカーソル `Cursor` とは、SQLの検索結果（複数行のレコード構造）を1行ずつ取り出して処理するためのポインタ（メモリ上の仕組み）のこと。
- 通常、SQLの SELECT 文を実行するとすべての該当データが一括で返されるが、カーソルを使用することで「1行読み込んで処理し、次の行へ進む」という手続き的な処理が可能になる
- データを一括で読み込むとメモリを圧迫してしまうが、カーソルを使うことでメモリに1つずつ展開してメモリ消費を抑えることができる。ただし、ただし、1つずつ読み込むため、処理速度は遅くなる
- 1行ずつ処理するとは、あくまでプログラム側のコード上の扱い（ループの回り方）の話であって、通信まで1行ずつ行なっているというわけではない。多くの場合ライブラリが裏側で数百〜数千件単位でまとめて通信を行なってくれているため、データ全件を一括で取得するよりは通信回数は増えてしまうが、1行ごとに毎回通信しているわけではない
- SQLインジェクション対策としてのプレースホルダーの利用は追加での理解が必要

## 8/30（日）

- `SparkSession.builder.getOrCreate()` は、プログラム内で Driverのベースとなる SparkSession（および内部の SparkContext）を生成・取得するためのコード
- コード上の `spark = SparkSession.builder.getOrCreate()` には、JVM上のSparkSessionを遠隔操作するための、PySpark（Python）のSparkSessionオブジェクトが変数 spark に入る
- Py4J を通じて JVM プロセスに命令が飛び、JVM（Driver）内に本家である Java/Scala の `org.apache.spark.sql.SparkSession` オブジェクトが生成され、Python側にラッパー（参照）オブジェクトが返される。Pythonプロセス側には、JVM上のその SparkSession を操作するためのPython版ラッパーオブジェクト（pyspark.sql.session.SparkSession）が生成され、変数 spark に代入される、という流れ
- `spark.stop()` を実行することで、Driver が Master にアプリケーションの終了を通知する。これを受けて Master/Worker が Executor プロセスを破棄（kill）し、CPU やメモリのリソースをクラスタ全体へ解放してくれる
- 「プログラムのコードを実行するという動作そのものが、CPUでしか行えない」という事実を前提にすることで多くの疑問が解けた
- Sparkの遅延評価が実現される仕組みを理解できた
- ① Transformations の呼び出し: 実際のデータ処理は行わず、Driver メモリに DAG（処理の設計図）を蓄積する
- ② Action の呼び出し: Catalyst オプティマイザが DAG 全体を解析・最適化し、物理実行計画を作成する
- ③ タスク化と分散実行: 物理プランを元に DAGScheduler / TaskScheduler が Task を作成し、Executor へ割り振って初めて実際のデータ処理が実行される
- Action操作とは、最終的にほしい結果が確定する時に使用する処理
- 集計関数を使用する場合は、指定項目がユニークになるようにデータを集計する必要がある
- `python3 -m モジュール名`: モジュールをスクリプトとして実行

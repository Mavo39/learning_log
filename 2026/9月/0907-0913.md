## 9/7（月）

- Python において `__file__` は、「現在実行されている .py ファイル自身のパス」を保持する特殊変数
- `Path(__file__).resolve().parent` を使用したことで、実行する場所を変えても問題なくスクリプトを実行できた
- トランザクションを使って、既存のRedshift内のデータの一部を更新する処理するスクリプトを開発
- これまでは基本、積み上げ型で処理する都度データが積みあがっていたが、より柔軟に既存データを変更して、別システムに反映できるようにしたいことから開発した
- これによって、既存データの更新処理途中で処理が止まってもデータを失わずに済む。かつ、トランザクションを概念としてではなく、実践として体感することができたのは大きな学びだった
- `__file__` は Python のスクリプトファイル（.py）として実行される際に定義される特殊変数であるため、.ipynb では使用できない
- globモジュールの `glob()` はリストを返すが、Pathオブジェクトの `glob()` はイテレータを返す 

```python
# リスト：1,000万個の要素をすべてメモリに生成・確保する 
# -> 数百MBのメモリを即座に消費 
hoge_list = [i for i in range(10_000_000)] 

# イテレータ（ジェネレータ）：要素の生成ルールだけを保持する 
# データ数に関わらず数十バイト程度のメモリしか消費しない 
hoge_iter = (i for i in range(10_000_000)) 
```

- `cursor.fetchall()` は、Redshift 上で実行された SQL の検索結果をすべて取り出し、手元のPythonのメモリ上に Python オブジェクト（タプル・リストの形式）として読み込む処理を行なう。
- だからこそ、`pl.DataFrame(...)` によってメモリ上に持ってきているリスト構造を、Polars のデータフレーム構造へと変換できる
- SQL側で絞り込みを細かく設定して複雑にするよりも、SQLでは最低限これだけ絞り込むという範囲を荒削りで決めて、あとはPolars側で絞り込みを行なって、最後にデータフレーム同士を semi join, inner join することで、コードのメンテナンス性が飛躍すると体感した（もともとSQL側でいらないデータを取得する、無駄な組み合わせ処理を行なっていた）
- タプル 1 個がデータベースの 1 レコード（1行）のデータ
- `cursor.fetchall()` によって、1行分のデータが縦に並んだリストを取得してくるので、そのままデータフレーム化できる

## 9/9（水）

- プログラムのライフサイクルは、大きく2つの段階に分かれる
- ① コンパイル： 人間が書いたプログラムを、コンピュータが理解できる形式に変換（翻訳）している段階
- ② ランタイム： 変換されたプログラムが、実際にコンピュータ上で動いている（実行されている）最中の段階
- Runtime Error は、コードの翻訳時には問題が見つからず、「実際に動かしてみたら途中で問題が発生して止まったエラー」を指す

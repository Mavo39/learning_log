 ## 9/3（木）

- commit はその時点でのプロジェクトのバックアップと捉えることができる
- 1つのコミットには1つの意味ある変更だけを載せることでコミットの粒度を整える
- これまで曖昧だった、ブランチ・HEAD・ワーキングディレクトリ・ステージングエリア・ローカルリポジトリの関係性と内部のディレクトリ構造を理解できたことによって、コマンドの意味を理解しながら具体的に何をしているのかがわかった
- ブランチは最新の1個のハッシュ値しか知らなくても、その先のCommitオブジェクトが「親は誰」と過去へリンクを繋いでいる（数珠つなぎになっている）ため、ブランチから過去のすべての変更履歴を追うことができる
- ブランチは最新の出口を指す看板として機能し、過去へ繋がる導線そのものはCommit同士が作っているという仕組み

- ターミナルマルチプレクサ（Terminal Multiplexer）: 1つのターミナル（端末）画面の中に、複数の仮想的な画面を作成・管理できるツール
- 本来は1つのウィンドウで1つのコマンドしか実行できないが、マルチプレクサを使うことで画面を分割したり、バックグラウンドで処理を動かし続けたりできるようになるため、これまでVS Code SSHでリモート接続して実行していた処理をより安全に行なうことができるようになった
- SSH接続のセッションが切れると処理が中断してしまうという課題を解決できた
- マルチプレクサを使うことで、作業状態がサーバー上のバックグラウンド（セッション）として維持される
- アタッチ（Attach）: セッションに接続して作業する
- デタッチ（Detach）: 作業状態を保ったまま一回画面を抜ける
- 回線が切れてもセッションは残っているため、再度SSH接続してアタッチすれば、「切断される直前の状態（開いていたファイルやコマンドの出力結果）」からそのまま作業を再開できる
- 自分のPC上でコンパイル・ビルドすることで、「自分の環境で確実に動作するバイナリ」をその場で作り出すことができる
- ソフトウェアの配布方法には、① パッケージ（完成品バイナリ）で配布する方式と② ソースコード（設計図）で配布する方式がある
- GIL（グローバルインタプリタロック） Python のメモリ管理を安全に行なうため、「同時に複数の CPU コアで Python のコードを実行させてはいけない」 という制限のこと。`threading` モジュールを使ってマルチスレッド化しても、内部的には「1つの CPU コアを高速に切り替えながら交互に実行しているだけ」になる
- GILのせいで「1プロセス＝実質1スレッド分のCPU計算力」という強力な制約が存在する
- 1プロセス1スレッドという実質的な壁があるので、プロセスを複数起動することでスレッドの壁を越えて並列処理を強制的に実現できる
- `curl` : Client URLの略。ブラウザを開くことなく、ターミナル上で直接サーバーと通信ができる
